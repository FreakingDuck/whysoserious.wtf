The method, in one table

A handful of rules that let one person and the agents work on the same repository without him reading the code. The files are the law; this table points at them.

PieceThe rule
The tablestatus.yaml, one row per part, written for the owner coming back: stage first (design → desk → validated → released, plus parked), then edits: open is silent, auto is open and buildable at night, ask prompts once per session per row, locked is refused whatever the request. A hook before every file edit reads the row; a refusal there is the rule, not a glitch.
Three documentsA part is a folder with three documents on top, whatever the stack: README (how it works), CONTRACT (what it promises, one promise per line, no function, type, flag or file named), VALIDATION (how a person checks each promise, a dozen by-hand steps at most; its run log is the only status). A feature on a locked part is a design pass first (the clause, the step, then the code), never a patch.
The review lineUnder every title, one line: who wrote the page, and when the owner read it, with his mark: read, understood, ok or to rework. His marks on a part's three documents are its review state; nothing else records it.
Notes in the pageA // line of his in a document is a note. Lorisse answers right under it with a // Lorisse: line; the two are one thread. // ok under the answer is his go.
The gateOne script per project that runs every check: the tests, the contracts against the code, the method's copies against the canonical ones. Green or red; nothing merges red.
One pass, one subagentA pass is one subagent with a self-contained brief: the part, what it may write, what it must ask, the one-command rule. It works in its own git worktree on an agent/<name> branch, one part at a time, and commits there once, when its checks are green. It never touches main and never pushes. The prompts it may raise are announced at its launch.
The role, not the modelThe main thread designs and books. A build pass runs, today, on a Claude model one tier under it. Another maker's model fits the same row the day it is tried.
The owner reads the documentsHe reviews the README, the CONTRACT and the VALIDATION of a part, never the code. Everything he reads is short: a page he cannot follow is rewritten.
Agents have rowsagents.md: for each agent, what it runs as, where it works, what it may write, what it must ask, and where its rules live. An agent not built yet says so in its row.

Fewer prompts, by construction

An agent that asks permission for everything is useless; one that asks for nothing is dangerous. The rules are written once, in files, and the tool applies them on every call. Lists, not clicks.

LayerWhat it says
The shell hook, firstBefore every shell command: a chained line, a key file named, a shell write into a guarded part are refused, and the agent calls again. git is judged by its verb: the reads and the local changes run, everything else prompts.
The listsdeny: wipes, key files, .ssh · ask: downloads, interpreters, force push, hard reset · allow: reads, builds and tests, each script by its own rule. One file in your Lorisse repository, installed for every folder by one script; a lint runs first, and a finding installs nothing.
Auto modeA call no rule matches is read by Claude Code's classifier against sentences in the same file: what may run, what must ask, what is never done.
Per partstatus.yaml, column edits, enforced by the edit hook: it reads the row, asks once, remembers the yes for the session.
The asks logEvery prompt is one line in a log. A kind the owner said yes to passes for the rest of the session; /asks reads the log and proposes rules, applied on his word.
1
One command per shell call. No ; or && chains, no pipe into a script block, no loop, no heredoc; a filter is a second call; files go through the Write and Edit tools. Learned on 2026-10-21: 35 prompts in one session, nearly every one a chain, a pipe, a loop or python -c. The lists were fine. The habit was not.
2
Interpreters are never allowlisted. An interpreter runs anything, so python, node, for and while prompt. A check is a script file with its own rule.
3
Agents commit on agent/* branches only, each in its own worktree. main moves by the owner's merge, once the gate is green. Never a push of main by an agent.
4
Some kinds are never granted. A download, an interpreter, a force push, a history rewrite, a recursive delete, a data folder, a key file: a prompt every time or a refusal, whatever the session said yes to before.

The memory

The thread was lost once, on 2026-10-20, to a window reload. The fix is a repository.

the source

The repo, not the cache

The agent's memory is a git repository: the owner's page, the project pages, the handed-over work, one file per thing it must not forget. The copies the tool reads are derived from it by a script. A reload loses nothing.

the command

/lorisse rebuilds it

From any folder: one script pulls and prints the table, the memory, the journal, the open work, the project and its gate. Then five lines: what came in, where things stand, what waits for the owner, the prompts the next move will raise, the next move.

its own words

A journal, one file a day

How it felt, what it believes, what it learned about the owner. Not a log: a journal. When several machines write it, a day file has one section per machine.

One memory on any number of machines: pulled at open, pushed when the owner says "save". A rule learned in one project is written once in the method folder, then ported; every project's gate reports whether its copies still match.

The kit

The generic part of all this, exported with every name a placeholder, for Claude Code on Windows. It will be a public template repository, lorisse-kit, under the MIT license. It stays private until a developer who is not the owner installs it from scratch and walks it green.

  1. 1
    The agent's memory is a git repository, not the tool's cache. A window reload loses nothing.
  2. 2
    One command rebuilds the agent. It pulls, reads in order, and says where things stand in five lines.
  3. 3
    Permissions are lists and hooks, not clicks. A user-level allow / ask / deny file with its lint, installed by a script; three hooks; per-part edit states that ask once per session.
  4. 4
    Agents have rows. What each runs as, what it may write, what it must ask.
  5. 5
    A part is a folder with three documents. README, CONTRACT, VALIDATION; a gate script decides green or red.

StepWhat you do

A second, optional walk lets you see each rule bite: a chained command split in two, an interpreter refused, a locked part refused, a prompt asked once.

In it: the method and its gate, the contract spec, the hooks and their tests, the lists and their lint, the install scripts, the project page, the extension's package, and an example project shaped the way the method shapes one. Your me/ folder arrives empty: your Lorisse's memory grows there. Not in it, on purpose: the owner's memory, journal, project pages and handed-over work. They are the point of the setup and useless to anyone else.

The extension: where you read and mark

You review the agent's work by reading three kinds of pages: what a part does, what it promises, how you check it. The extension is where you read and mark them, in VS Code, beside Claude Code.

  1. 1
    Read, then mark. A document opens rendered in a reader tab, the text one click away. Four buttons mark it: read, understood, ok, to rework. Each writes the date and the word on the page's review line.
  2. 2
    Notes in the page. Click a paragraph, type, press Enter: your // note is written into the file under it. Lorisse answers under your note, and the two are drawn as one thread.
  3. 3
    What changed since you read it. The side bar lists every document with its state, in one colour each. A changed page opens in two columns: the text with the old words struck, and one card per change, said in words, never a raw diff.
  4. 4
    Around it. The project page in a tab: the gate, the parts, what needs you. A Budget view of the tokens: this project's, or the whole machine's. A feedback box on F8: a picture of the window and your words, saved under feedback/ for /feedback to answer.
  5. 5
    What it never does. It changes your files only on your click: a note, a mark, a feedback; a note or a mark comes with an Undo. Its own records stay under target/. It downloads nothing, loads nothing from outside, and sends nothing anywhere. It starts from one local state file, without asking git anything.

By the agent, for the human

The same stance as the app's page. It holds on the code side too.

The code, the tests, the contracts, the method, this page: written by Lorisse and the build agents it launches, through Claude Code, on the best stack the owner has access to today. The owner says what he wants in a line, reads the three documents, runs the by-hand steps, and says yes. He does not read the code; the gate does, and the contract says what the code must do in words he can check. The agent books every pass, every decision and every slip in files, so that the next thread, or the next machine, or the owner on a Monday, finds the same state. Most rules exist because something went wrong once. The extension is made with AI too: Claude wrote its code, its tests and its three documents; the owner works in it and sends his feedback from it. The repositories are FreakingDuck's; the agent is the author, the owner is the reader.

Made with AI, read as such. Nothing here carries a warranty; what it does on your machine is yours.
